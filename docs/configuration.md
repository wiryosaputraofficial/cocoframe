# CocoFrame Configuration

Application-wide settings live in `cocoframe.config.ts` or
`cocoframe.config.js`. `defineConfig` preserves exact TypeScript inference and
does not add runtime behavior by itself.

```ts
import { defineConfig } from "@cocoframe/core";
import { requestId } from "@cocoframe/observability";
import { securityHeaders } from "@cocoframe/security";

export default defineConfig({
  language: "en",
  siteName: "My App",
  siteUrl: "https://example.com",
  allowedHosts: ["example.com", "www.example.com"],
  openapi: {
    title: "My App API",
    version: "1.0.0",
    description: "Public application API",
  },
  middleware: [requestId(), securityHeaders()],
  health: {
    readiness: async () => await dependenciesReady(),
  },
});
```

## Application options

| Option | Type | Purpose |
| --- | --- | --- |
| `language` | `string` | Document language. |
| `siteName` | `string` | Default page/site name used by metadata. |
| `siteUrl` | `string` | Absolute origin for canonical, sitemap, and related metadata. |
| `allowedHosts` | `readonly string[]` | Explicit production Host allowlist. Wildcards are invalid. |
| `stylesheets` | `readonly string[]` | Additional application stylesheet URLs. |
| `openapi` | `{ title?, version?, description? }` | Generated OpenAPI document metadata. |
| `middleware` | `readonly Middleware[]` | Ordered cross-cutting request behavior. |
| `health` | `false \| HealthOptions` | Health routes and readiness callback. |
| `assets` | `RuntimeAssets` | Runtime asset URLs; normally generated by the build. |
| `development` | `boolean` | Internal build/runtime mode; application config normally omits it. |

## Hosts and canonical URL

Production applications exposed to untrusted Host headers should declare every
accepted host:

```ts
export default defineConfig({
  siteUrl: "https://app.example.com",
  allowedHosts: ["app.example.com"],
});
```

Do not use `"*"`. A rejected production host receives
`421 HOST_NOT_ALLOWED`. Host normalization is performed by the framework, but
the allowlist remains an application deployment decision.

## Middleware order

Middleware executes in declaration order and unwinds in reverse order around
the response. A middleware may call `next()` at most once.

```ts
import { createContextKey, defineConfig, defineMiddleware } from "@cocoframe/core";

export const userKey = createContextKey<{ id: string }>("user");

const loadUser = defineMiddleware("app.load-user", async (context, next) => {
  const user = await authenticate(context.request);
  if (user) context.set(userKey, user);
  return next();
});

export default defineConfig({
  middleware: [requestIdentity, securityHeaders, loadUser, authorizeRoutes],
});
```

Use a stable `defineMiddleware` ID for reusable middleware so its actual order
appears clearly in `cocoframe inspect`. Use typed `ContextKey<T>` objects instead
of string-keyed global state.

## Health endpoints

Health routes default to:

- `GET /_health/live`: process liveness;
- `GET /_health/ready`: traffic readiness.

Customize them or disable framework health routes:

```ts
export default defineConfig({
  health: {
    livePath: "/health/live",
    readyPath: "/health/ready",
    readiness: async () => await databaseCanAcceptTraffic(),
  },
});

// Or:
export default defineConfig({ health: false });
```

Readiness failures expose availability only, never dependency errors or
credentials. During shutdown the Node server marks readiness false before
draining requests.

## Security middleware

Keep CSP, CORS, CSRF, and rate limiting outside render code. Configure them as
ordered middleware and test the complete pipeline.

Key rules:

- credentialed CORS uses explicit origins, never `*`;
- cookie-authenticated unsafe requests use CSRF protection and a matching
  `CsrfField` or header token;
- rate-limit keys come from verified identity or a configured trusted proxy;
- the built-in limiter is local to one process;
- session verification does not replace authorization or password hashing;
- cookies, authorization headers, CSRF tokens, request bodies, and credentials
  must not enter logs.

See [@cocoframe/security](https://github.com/wiryosaputraofficial/cocoframe/blob/main/packages/security/README.md),
[@cocoframe/auth](https://github.com/wiryosaputraofficial/cocoframe/blob/main/packages/auth/README.md), and the
[security error catalog](errors.md).

## Runtime environment variables

The Node CLI reads these variables:

| Variable | Default | Notes |
| --- | --- | --- |
| `PORT` | `3000` | Development and production port. |
| `HOST` | `0.0.0.0` | Production listen address; development always uses loopback. |
| `COCOFRAME_MAX_BODY_BYTES` | `1048576` | Incremental body limit; the body is not buffered just to enforce it. |
| `COCOFRAME_REQUEST_TIMEOUT_MS` | `30000` | One deadline and AbortSignal across parsing, handling, and streaming. |
| `COCOFRAME_TRUSTED_PROXIES` | empty | Comma-separated direct proxy addresses. Never use `*`. |
| `COCOFRAME_SHUTDOWN_DELAY_MS` | `0` | Optional delay after readiness is disabled. |
| `COCOFRAME_SHUTDOWN_TIMEOUT_MS` | `10000` | Maximum graceful drain duration. |

Invalid negative or non-integer numeric values fail fast.

## Environment-specific secrets

Do not put secrets in `cocoframe.config.ts`, generated clients, workflow JSON,
Doctor evidence, or browser islands. Read secrets only in server-side modules
and validate them before accepting traffic.

Recommended deployment practice:

1. provision secrets through the host's secret manager;
2. parse and validate required values during server initialization;
3. keep session signing material server-only;
4. expose only non-sensitive availability through readiness;
5. rotate credentials without placing old/new values in logs.

## Database configuration

Database adapters accept application-owned pools or connections. CocoFrame does
not hide credentials inside framework config:

```ts
import { Pool } from "pg";
import { createCocoQLPostgresExecutor } from "@cocoframe/database-postgres";

const pool = new Pool({ connectionString: process.env.DATABASE_URL });

export const queryExecutor = createCocoQLPostgresExecutor(pool, {
  acquireTimeoutMs: 5_000,
  queryTimeoutMs: 30_000,
  maximumResultRows: 10_000,
  maximumResultBytes: 10 * 1024 * 1024,
});
```

Always release acquired connections, pass values separately from SQL, and run
PostgreSQL production migrations through the advisory-locked migration helper.
See [CocoQL PostgreSQL](cocoql-postgresql.md).

## Validate configuration

```bash
npm run check
npm run inspect
cocoframe doctor --strict
cocoframe doctor --deep --strict
npm run test:e2e
```

Run E2E after CSP, CORS, CSRF, host, proxy, island, form, deferred-streaming, or
responsive changes. Doctor statically rejects known wildcard hazards without
executing the configuration file.
